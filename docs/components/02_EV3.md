The **LEGO Mindstorms EV3 Intelligent Brick** is the main controller of Piolín. Every major autonomous decision made by the final robot ultimately passes through the EV3, including propulsion, steering, wall navigation, corner handling, floor-color interpretation, safety decisions, and obstacle-avoidance commands.

Piolín experimented with other processing architectures during development, but the final system keeps the EV3 at the center of the robot. This was not simply because it was the original controller. The EV3 provides a convenient connection point between the LEGO motors, the three ultrasonic sensors, the color sensor, and the higher-level navigation program. Keeping these fundamental systems on one controller reduces the number of communication layers required for normal driving.

The vision subsystem is the main exception. The HuskyLens performs visual recognition separately and communicates with an Arduino Nano, which then transfers the relevant information to the EV3 through USB. Even in this configuration, the EV3 remains the controller that decides how the robot reacts.

> [!IMPORTANT]
> The Arduino Nano and HuskyLens extend Piolín's perception capabilities, but they do **not** replace the EV3 as the main vehicle controller.

---

## 2.1 Role of the EV3 in Piolín

The EV3 acts as the point where Piolín's sensing and actuation systems come together.

On the input side, it receives distance information from three ultrasonic sensors and floor information from the color sensor. During the Obstacle Challenge, it can also receive processed vision information from the Arduino Nano through USB.

On the output side, the EV3 controls the motor responsible for propulsion and the separate motor responsible for steering. This means that the same controller that interprets the current track situation is also directly responsible for changing the robot's motion.

The basic control relationship is:

```text
                     SENSOR INPUTS
                          │
                          ▼
                ┌───────────────────┐
                │     LEGO EV3      │
                │  Main Controller  │
                └─────────┬─────────┘
                          │
                  Navigation Decision
                          │
             ┌────────────┴────────────┐
             ▼                         ▼
       DRIVE MOTOR                STEERING MOTOR
        Port A                       Port B
             │                         │
             ▼                         ▼
       Propulsion               Ackermann Steering
```

This architecture is important because it creates a direct relationship between sensing and movement. The EV3 does not need to send every basic navigation decision through another processor before it reaches the motors.

## 2.2 Final EV3 Port Assignment

Piolín uses the EV3 input and output ports according to the following final configuration:

| EV3 Interface | Connected Component | Function in Piolín |
| :--- | :--- | :--- |
| **Motor Port A** | Drive Motor | Controls vehicle propulsion |
| **Motor Port B** | Steering Motor | Controls the front Ackermann steering mechanism |
| **Sensor Port S1** | Front Ultrasonic Sensor | Frontal emergency collision detection |
| **Sensor Port S2** | Right Ultrasonic Sensor | Measures right-side wall distance |
| **Sensor Port S3** | Left Ultrasonic Sensor | Measures left-side wall distance |
| **Sensor Port S4** | LEGO Color Sensor | Reads blue/orange floor markings |
| **USB** | Arduino Nano | Receives information from the vision subsystem |

The final port arrangement can also be visualized as:

```text
                   LEGO EV3
        ┌─────────────────────────┐
        │                         │
        │   A  → Drive Motor      │
        │   B  → Steering Motor   │
        │                         │
        │   S1 → Front US         │
        │   S2 → Right US         │
        │   S3 → Left US          │
        │   S4 → Color Sensor     │
        │                         │
        │   USB ↔ Arduino Nano    │
        │                         │
        └─────────────────────────┘
```

This port map is part of the final Piolín architecture and should remain consistent throughout the repository.

## 2.3 Motor Control Through the EV3

Piolín separates propulsion from directional control.

The **drive motor on Port A** is responsible for moving the robot along the track. The **steering motor on Port B** changes the angle of the front wheels through the Ackermann steering mechanism.

This separation allows the software to control speed and steering independently.

For example, the EV3 can reduce propulsion speed while maintaining a strong steering command during a difficult corner. It can also continue driving at a higher straight-line speed while applying only a small steering correction.

Conceptually:

```text
                     EV3
                      │
           ┌──────────┴──────────┐
           │                     │
           ▼                     ▼
       MOTOR A                MOTOR B
     Propulsion              Steering
           │                     │
           ▼                     ▼
      Rear Drive          Front Ackermann
```

The motor encoders also give the software a repeatable reference for movement. The steering motor encoder is especially important because Piolín uses a defined mechanical center position before beginning a run. Once the front wheels are physically aligned, the steering motor angle can be reset so that the software treats that position as its neutral reference.

The important distinction is that the steering motor encoder measures **motor rotation**, not the exact physical angle of the front wheels. The mechanical linkage converts motor movement into wheel steering, so the relationship between encoder position and actual wheel angle must be calibrated experimentally.

## 2.4 Sensor Acquisition

The EV3 directly receives the measurements used for Piolín's basic autonomous navigation.

The two lateral ultrasonic sensors on S2 and S3 measure the robot's relationship with the left and right track walls. Their interpretation changes according to the direction of travel. Depending on whether Piolín is travelling clockwise or counterclockwise, one becomes the inner-wall reference while the other becomes the outer-wall reference.

The front ultrasonic sensor on S1 has a different responsibility. It does not participate in the normal inner-wall and outer-wall calculations. Instead, it provides an independent safety measurement directly ahead of the robot. If the frontal distance becomes critically small and the condition is confirmed, the EV3 can stop the propulsion motor before normal navigation continues into a possible collision.

The color sensor on S4 provides information about the floor markings. The EV3 interprets these readings to determine the initial direction and to track progress around the course.

This produces three different types of information inside the same controller:

```text
LATERAL ULTRASONICS
        │
        ▼
Track geometry
Inner / Outer walls


FRONT ULTRASONIC
        │
        ▼
Emergency frontal safety


COLOR SENSOR
        │
        ▼
Direction and track progress
```

Keeping all three types of navigation information available to the EV3 allows the main program to determine which input should have priority at any given moment.

## 2.5 EV3 as the Navigation Decision Layer

The EV3 does more than read sensors individually. Its main role is to interpret them according to the current state of the robot.

A distance measurement does not always mean the same thing. For example, a large reading from the inner ultrasonic sensor during a straight section may suggest that Piolín has moved away from the wall. Near a corner, however, the same type of reading may indicate that the wall has physically disappeared.

The EV3 software is responsible for distinguishing between those situations.

The decision flow can be simplified as:

```text
Read sensors
     │
     ▼
Interpret current geometry
     │
     ▼
Determine current navigation state
     │
     ▼
Apply safety priorities
     │
     ▼
Calculate steering and speed
     │
     ▼
Command motors
```

This is why the EV3 is considered the **main controller** rather than simply a motor controller.

It combines sensor measurements with the current navigation state before producing a movement command.

## 2.6 Software Environment

Piolín is programmed in **Python using the Pybricks environment for the EV3**.

The software creates an `EV3Brick` object and directly initializes the motors and sensors using their assigned ports. This provides a clear relationship between the physical wiring and the software architecture.

A simplified representation of the final hardware initialization is:

```python
from pybricks.hubs import EV3Brick
from pybricks.ev3devices import Motor, UltrasonicSensor, ColorSensor
from pybricks.parameters import Port

ev3 = EV3Brick()

drive = Motor(Port.A)
steer = Motor(Port.B)

us_front = UltrasonicSensor(Port.S1)
us_right = UltrasonicSensor(Port.S2)
us_left = UltrasonicSensor(Port.S3)

color_sensor = ColorSensor(Port.S4)
```

This direct mapping is valuable for reproducibility because another person looking at the source code can immediately relate each object to a physical EV3 connection.

```text
CODE                    PHYSICAL ROBOT

Port.A      ────────→   Drive Motor
Port.B      ────────→   Steering Motor
Port.S1     ────────→   Front Ultrasonic
Port.S2     ────────→   Right Ultrasonic
Port.S3     ────────→   Left Ultrasonic
Port.S4     ────────→   Color Sensor
```

The final software documentation explains the navigation algorithms in more detail. From a hardware perspective, the important point is that Pybricks allows the EV3 program to read sensors and command motors from the same execution environment.

## 2.7 State-Based Control

Piolín's navigation is not based on one steering equation running identically throughout the entire track.

Instead, the EV3 executes different behaviors according to what the robot is currently experiencing.

A simplified example is:

```text
START
  │
  ▼
Determine direction
  │
  ▼
Follow inner wall
  │
  ▼
Detect corner
  │
  ▼
Use outer wall during turn
  │
  ▼
Reacquire inner wall
  │
  ▼
Stabilize
  │
  ▼
Continue navigation
```

At the same time, safety conditions can interrupt the normal sequence. The front ultrasonic sensor can request an emergency stop if Piolín is approaching something dangerously close.

This means that the EV3 is continuously balancing normal navigation with safety behavior rather than blindly executing a fixed sequence of motor commands.

The complete state-machine design is documented separately in the software section.

## 2.8 Communication With the Vision Subsystem

The EV3 does not process the HuskyLens camera image directly.

Instead, visual recognition is handled by the HuskyLens, while the Arduino Nano acts as the communication interface between that vision system and the EV3.

The architecture is:

```text
             VISUAL SCENE
                  │
                  ▼
             HUSKYLENS
                  │
                  ▼
            ARDUINO NANO
                  │
                 USB
                  │
                  ▼
               LEGO EV3
                  │
                  ▼
        Navigation Decision
                  │
         ┌────────┴────────┐
         ▼                 ▼
      DRIVE             STEERING
```

This division prevents Piolín's main controller from needing to interpret a complete raw image stream.

The EV3 receives only the information that is relevant to the navigation logic and then decides how that information should affect steering and propulsion.

This distinction is particularly important during the Obstacle Challenge. The camera can identify a pillar, but the EV3 still has to combine that information with wall distances and safety conditions before deciding how the robot should move.

## 2.9 Hardware Priority and Safety

The EV3 is also responsible for enforcing the priority between different hardware inputs.

Not every sensor should have equal control authority at all times.

For example, the HuskyLens may request an obstacle-avoidance maneuver, but the lateral ultrasonic sensors may simultaneously indicate that the requested movement would bring Piolín too close to a wall. Similarly, normal wall navigation should not continue if the front ultrasonic sensor detects an immediate frontal collision risk.

The hardware-control priority can therefore be visualized as:

```text
        HIGHEST PRIORITY
               │
               ▼
     Front collision safety
               │
               ▼
       Lateral wall safety
               │
               ▼
       Obstacle strategy
               │
               ▼
        Corner handling
               │
               ▼
     Normal wall following
               │
               ▼
         LOWER PRIORITY
```

The exact software arbitration is documented elsewhere, but the EV3 is the device responsible for applying that hierarchy to the motors.

## 2.10 Onboard Feedback and Debugging

Another useful feature of the EV3 during development is that the robot can provide immediate information without needing an external computer connected during every test.

The EV3 screen can display values such as the current navigation state, detected direction, sensor distances, line counts, or debugging information. The built-in speaker can also provide short audio signals when important events occur during testing.

For example:

```text
EV3 SCREEN

PIOLIN
DIRECTION: CW
STATE: FOLLOW
LEFT: 430
RIGHT: 420
```

During development, this type of onboard feedback is useful because it allows the team to distinguish between a sensing problem and a mechanical problem.

If Piolín turns incorrectly but the EV3 screen shows that the correct wall and state were detected, the problem may be related to steering behavior rather than sensing. If the screen displays an incorrect distance or state transition, the team can investigate the sensing or software logic instead.

The screen and speaker are therefore not essential navigation sensors, but they are valuable engineering tools for testing and diagnosis.

## 2.11 Why the EV3 Was Retained as the Main Controller

Piolín's development included experiments with more complex computing architectures. However, greater processing capability does not automatically produce a better competition robot.

The final design prioritizes **system integration and predictable behavior**.

Most of Piolín's essential navigation information comes from relatively compact sensor data: ultrasonic distances, color detections, motor encoder positions, and simplified vision detections. These tasks do not require the main controller to process a continuous high-resolution video stream.

Keeping the EV3 as the primary controller therefore allows the robot to use its LEGO sensors and motors directly while delegating the specialized visual-recognition task to the HuskyLens subsystem.

The result is a distributed architecture:

```text
EV3
│
├── Vehicle control
├── Sensor interpretation
├── Navigation
├── Steering
├── Propulsion
└── Safety decisions


Arduino Nano
└── Vision communication


HuskyLens
└── Visual recognition
```

Each processor or device has a clearly defined responsibility.

This is preferable to adding computing hardware that duplicates functions already handled effectively by the EV3.

## 2.12 Integration With the Open Challenge

During the Open Challenge, the EV3 can perform the fundamental navigation task without depending on the HuskyLens vision subsystem.

The active control relationship is approximately:

```text
          Front US
             │
Left US ─────┼───── Right US
             │
        Color Sensor
             │
             ▼
          LEGO EV3
             │
      ┌──────┴──────┐
      ▼             ▼
   Drive          Steering
```

The lateral ultrasonic sensors provide track geometry, the front ultrasonic sensor provides an emergency safety layer, and the color sensor provides information about direction and progress.

This independence is valuable because a vision-system problem does not automatically remove Piolín's ability to perform basic track navigation.

## 2.13 Integration With the Obstacle Challenge

The Obstacle Challenge adds the HuskyLens and Arduino Nano to the same EV3-centered architecture.

```text
        HuskyLens
            │
            ▼
      Arduino Nano
            │
           USB
            │
            ▼

 Front US ──┐
 Right US ──┼──→ LEGO EV3 ──→ Drive + Steering
 Left US  ──┤
 Color    ──┘
```

The EV3 now receives both geometric information from the ultrasonic sensors and visual obstacle information from the camera subsystem.

This allows Piolín to make decisions using more than one type of perception.

For example, vision may determine which side of a colored pillar should be used for avoidance, while the ultrasonic sensors continue providing information about the surrounding track walls.

The EV3 remains responsible for combining those inputs into one final motor command.

## 2.14 Failure Isolation

One reason for separating the robot into subsystems is that problems become easier to diagnose.

If the HuskyLens or Nano communication fails, the fault belongs primarily to the vision subsystem. The EV3, drive motor, steering motor, ultrasonic sensors, and color sensor can still be tested separately.

If one ultrasonic sensor gives inconsistent measurements, that sensor can be isolated without changing the entire vision architecture.

If the robot receives correct sensor information but the wheels do not follow the expected trajectory, the steering or drivetrain can be investigated independently.

This can be represented as:

```text
VISION ERROR
    │
    └── Check HuskyLens / Nano / USB


DISTANCE ERROR
    │
    └── Check S1 / S2 / S3 sensors


COLOR ERROR
    │
    └── Check S4 / calibration / lighting


MOTION ERROR
    │
    ├── Check Port A drivetrain
    └── Check Port B steering


LOGIC ERROR
    │
    └── Check EV3 software/state
```

This modularity was one of the reasons the final architecture became simpler than several earlier prototypes.

## 2.15 Final EV3 Integration Summary

The LEGO EV3 is the central coordination point of Piolín's final competition architecture.

| EV3 Responsibility | Final Role |
| :--- | :--- |
| **Propulsion** | Commands the Port A drive motor |
| **Steering** | Commands the Port B steering motor |
| **Frontal Safety** | Reads the S1 front ultrasonic sensor |
| **Right-Wall Sensing** | Reads the S2 ultrasonic sensor |
| **Left-Wall Sensing** | Reads the S3 ultrasonic sensor |
| **Floor Detection** | Reads the S4 color sensor |
| **Vision Integration** | Receives information from the Arduino Nano through USB |
| **Navigation Logic** | Determines current behavior and state transitions |
| **Safety Arbitration** | Determines when safety should override normal navigation |
| **Testing / Diagnostics** | Provides onboard screen and speaker feedback |

Piolín therefore does not use the EV3 merely because it is compatible with LEGO hardware. It remains the main controller because the final architecture is intentionally organized around direct sensor-to-decision-to-actuator control.

The hardware relationship can be summarized in one diagram:

```text
                           HUSKYLENS
                               │
                               ▼
                         ARDUINO NANO
                               │
                              USB
                               │
                               ▼
                    ┌────────────────────┐
                    │      LEGO EV3      │
                    │   MAIN CONTROLLER  │
                    └─────────┬──────────┘
                              │
       ┌──────────────┬───────┼───────┬──────────────┐
       │              │       │       │              │
       ▼              ▼       ▼       ▼              ▼
   FRONT US       RIGHT US  LEFT US  COLOR       MOTOR OUTPUT
     S1              S2       S3      S4          A + B
       │              │       │       │              │
       └──────────────┴───────┴───────┘              │
                       │                              │
                       ▼                              ▼
               PERCEPTION DATA               DRIVE + STEERING
```

The final system keeps the responsibilities clear: the sensors measure the environment, the vision subsystem identifies obstacles, and the EV3 decides how Piolín should respond.
